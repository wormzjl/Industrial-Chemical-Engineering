Three overloads that only forwarded a constant are gone and their callers pass it: the private 8-argument `calculate` (`NewtonTrace.NONE`), the 5-argument `diagnostics` (trailer `null`), the 6-argument `recoverWithDrawRamp` (`coupled` `false`).

Four are the same two calls in the same order, keeping only the corrected pass: the dry-top or pot direct solve and its base solve in `calculateBranch`, a feature-ramp rung and the ramp's request retry. The other four stay: the material-closed fallback, the coarse recovery, the stage grid and the pressure leg each differ in a call, a wrap, an event or by keeping the correction's verdict (`PhaseCorrection.attempted()`).

## Points where compiling or binding is not certain

I could not compile. Each point is legal Java as far as I can read the language specification, and each was checked by reading.

1. `RungOptions.java` lines 12 to 20: a package-private top-level record whose components name the package-private nested `V3ColumnCalculator.ContinuationJacobianPolicy` and `V3SimultaneousColumnSolver.RungBudget` and `Extension` (both nested records with no modifier in the package-private `V3SimultaneousColumnSolver`). No explicit canonical constructor, so the implicit one has the record's package access (JLS 8.10.4).
2. `V3ColumnCalculator.java` lines 911 to 919: two `solveSingleProblem` overloads of arities 7 and 8 with different parameter types at positions 6 to 8; each call in the file has one applicable overload. `V3HydraulicPublish.java` 187 and `V3LearnedRoute.java` 173 call the 8-argument pp one from another class; the 7-argument one is private and so not potentially applicable there (JLS 15.12.2.1), and has the wrong arity anyway.
3. `V3ColumnCalculator.java` lines 920 to 926: the old 11-argument body reassigned its parameter `jacobianPolicy`; it is now a local declared from `rung.jacobianPolicy()` after the iteration check, and `maximumIterations`, `budget`, `extension` are locals read from the record at the top (reads of record fields: no side effect, so the order of the checks and their messages is the old one). The body has no lambda (its arrows are switch cases; its method references are `thermo::newWorkspace`), so no effectively-final rule applies to these locals.
4. `RungOptions.of` reads `RungBudget.DEFAULT` and `Extension.NONE` at the call site instead of inside the removed overloads. Argument expressions are evaluated left to right before the call, as before; the only moved reads are these two static fields, which have no side effects (class initialization of the two nested records happens at the first solve of a JVM either way). In `V3LearnedRoute` line 174 to 175 `neuralRungBudget(options)` and `neuralExtension(options)` are now evaluated before `policy` and `wet` (plain locals): still budget first, then extension, so an `IllegalArgumentException` from either constructor is thrown in the same order and caught by the same handler in `calculateInCatalog`.
5. `V3ColumnCalculator.java` lines 164 and 171: calls of the private 9-argument `calculate` with `null` or a `Consumer` in position 7 and `NewtonTrace.NONE` in position 9; it is the only 9-argument `calculate`. `0, 0` still widen to `double`.
6. `runRung` (`V3ColumnCalculator.java` line 1155) adds one frame of `V3ColumnCalculator` under four rung kinds. Stack-reading code in the repository matches only on class names (`CrudeUnitSampleTest` lines 242, 874, 1228: a frame whose class contains `V3ColumnCalculator`, which every solve has anyway) or reads other packages; `tools/tutorial-column/SmallColumn.java` sorts polls by a `V3ColumnCalculator` frame, `correctNeuralSeed` or a `Neural` class (D-C2 summary item 10), none of which `runRung` changes. One frame more cannot change a result.
7. `V3ColumnCalculator.java` line 504 and `V3LearnedRoute.java` line 185 pass `null` as the `String trailer`; with one 6-argument `diagnostics` there is nothing for a `null` to make ambiguous.
